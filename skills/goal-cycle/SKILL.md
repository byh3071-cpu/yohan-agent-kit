# 골 사이클

승인된 결정 아래에서 목표를 작은 검증 단위로 진행한다. 현재 프로젝트의 규칙과 활성 로스터를 우선하며 특정 PC 경로, 모델 이름, CLI 순서를 보편 규칙으로 가정하지 않는다.

## 컨텍스트를 먼저 확인한다

다음 순서로 필요한 범위만 읽는다.

1. 현재 파일에서 가장 가까운 `AGENTS.md`, `CLAUDE.md`, `RULES.md`와 프로젝트 문서
2. 활성 goal, 관련 ADR, Git 상태·이력, 테스트·CI 계약
3. 프로젝트가 연결한 공통 로스터·용어집·Orca 계약
4. 현재 대화와 사용자가 직접 제공한 자료

근거가 충돌하면 확정 사실, 제안, 미해결 충돌로 나눈다. 로컬에 없는 경로나 도구를 있다고 가정하지 않는다. 생태계 도구와 용어를 대조할 때만 [운영 참고](reference.md)를 읽는다.

## 결정 게이트를 먼저 확인한다

다음처럼 되돌리기 비용이 큰 미확정 결정이 목표에 포함되면 `$adr-cycle`로 먼저 분류한다.

- SoT·시스템 책임·다레포 경계
- 데이터베이스·인증·보안·프레임워크 선택
- 여러 프로젝트나 에이전트의 책임 충돌

관련 ADR이 `Proposed`이면 조사·계획까지만 진행하고 그 결정에 의존하는 구현은 멈춘다. `Accepted`이면 ADR 경로, 결정, 제약, 후속 작업을 목표 입력에 포함한다. 낮은 비용의 구현 선택에 가짜 ADR을 만들지 않는다.

ADR 상태는 사용자의 말이나 handoff 문구만 믿지 않고 실제 파일에서 확인한다.

1. 가장 가까운 규약으로 ADR 파일을 찾고 프로젝트가 사용하는 상태 표면을 읽는다. frontmatter와 본문 상태가 둘 다 있으면 서로 같은지 확인한다.
2. 파일·경로가 없거나 프로젝트가 요구하는 상태 표면이 빠졌거나 함께 존재하는 상태가 다르면 결정 의존 구현을 멈추고 불일치를 보고한다.
3. handoff의 결정·제약과 실제 ADR 내용이 다르면 임의 병합하지 않는다. 실제 파일을 기준으로 차이를 제시하고 해소될 때까지 멈춘다.
4. `Superseded`이면 대체 ADR 링크를 따라가 현재 결정을 다시 확인한다. 대체 문서가 없거나 순환하면 멈춘다.
5. `Deprecated`이거나 프로젝트의 철회 상태이면 그 결정을 새 구현 근거로 사용하지 않는다.
6. 최종적으로 확인한 현재 ADR이 `Accepted`일 때만 결정 의존 구현을 연다.

ADR에서 목표로 넘길 때는 경로·확정 결정·제약·후속 작업뿐 아니라 **미해결 위험**과 **남은 사람 게이트**도 보존한다.

## 하드 게이트

1. 프로젝트가 요구하는 스펙·설계 승인을 받기 전에는 만들기를 시작하지 않는다.
2. 만든 이와 검수하는 눈을 분리한다. 검수는 구현의 다른 이름이 아니다.
3. 사람만 통과시킬 수 있는 ADR 승인·Plan 승인·머지 판정을 자동 처리하지 않는다.
4. 성공 정의에 앞뒤 단계가 같은 결과를 뜻하는지 확인하는 악수 한 줄을 둔다.
5. 시크릿, 배포, 전역 홈 쓰기 같은 별도 승인 게이트를 우회하지 않는다.
6. 언어·PR·커밋 규칙은 가장 가까운 프로젝트 지침을 따른다.

## 크기를 판정하고 선언한다

작업 전에 프로젝트의 라우팅 규칙으로 `라우팅: S|M|L — 계획 1줄 (근거)`를 선언한다. 프로젝트가 파일 수, 위험, 하드 트리거를 정의했다면 그 기준이 우선한다.

| 판정 | 기본 실행 방식 |
|---|---|
| S | 주 에이전트가 직접 수행하고 필요한 검증을 붙인다. |
| M | 탐색·구현·검수 역할을 프로젝트의 서브에이전트 규칙에 맞춰 나눈다. |
| L | Plan 승인 뒤 활성 goal과 Orca worktree·멀티에이전트 실행 계약을 사용한다. |

애매하면 작은 쪽으로 시작하고 범위나 위험이 늘면 재선언한다. Orca와 `/goal`은 L 작업에서 해당 환경이 제공할 때만 사용한다.

프로젝트에 라우팅 규칙이 없을 때도 다레포 변경, 스키마 마이그레이션, 인증·결제·보안 변경, 릴리즈는 **최소 L**로 판정한다. 이 하한은 파일 수가 적어도 낮추지 않는다. 그 밖의 작업은 실제 범위·의존성·복구 비용으로 S/M/L을 정하고, 임의의 범용 파일 수 기준을 새 규칙처럼 만들지 않는다.

## 12단계로 진행한다

Plan 범위는 기본적으로 1~4단계다.

1. **조사** — 저장소와 실제 근거를 읽고 사실·가정·미확정을 분리한다.
2. **스펙** — 무엇을, 비범위, 성공 정의, 악수를 적는다.
3. **설계** — 구조, 책임 경계, 데이터 흐름, 위험, 복구 방식을 정한다.
4. **티켓나누기** — 작은 검증 단위와 의존 순서를 정하고 필요한 사람 승인을 기다린다.
5. **만들기** — 승인된 티켓 순서로 구현한다.
6. **검증** — 테스트·CI·결정론 체크로 성공 정의를 증명한다.
7. **검수** — 만든 이와 다른 눈으로 실패·회귀·경계 누락을 찾고 blocker면 만들기로 돌려보낸다.
8. **품질확인** — 보안·성능·접근성·운영성 등 목표 위험에 맞는 품질 축을 확인한다. 작은 작업은 6~7단계에 합칠 수 있다.
9. **PR올리기** — 의도·증거·남은 위험을 기록하고 PR을 열되 머지하지 않는다.
10. **머지판정** — 사람이 검증 결과와 위험을 보고 결정한다.
11. **지켜보기** — 머지·배포 뒤 실제 동작과 회귀를 관찰한다.
12. **다듬기** — 재발 방지 문서·패턴·자동화를 역전파한다.

## 실행 환경은 조건부로 사용한다

- 모델·CLI 순서와 AGY 역할은 활성 `agent-roster` 또는 가장 가까운 지침에서 읽는다. 하드코딩한 우회 순서를 만들지 않는다.
- AGY가 보조 전용이면 그 산출물을 규정된 상위 티어가 검증해야 한다.
- `worker_done`, `wait-failover`, quota 전환은 현재 Orca 계약이 제공하는 L 실행에서만 적용한다.
- 외부 도구가 없거나 인증되지 않았으면 그 사실을 보고하고, 승인 게이트를 유지한 채 가능한 로컬 검증으로 진행한다.
