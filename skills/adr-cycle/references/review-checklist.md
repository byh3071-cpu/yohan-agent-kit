# ADR 수명주기·검토 체크리스트

ADR을 검토하거나 상태를 바꿀 때 이 문서를 사용한다. 프로젝트 자체 규약이 다르면 그 규약이 우선한다.

## 입력 완전성

- 결정 질문이 한 문장으로 특정되어 있는가?
- 범위와 비범위가 분리되어 있는가?
- 결정 동인과 제약이 실제 근거에 연결되는가?
- 되돌리기 비용과 영향을 받는 구성요소가 드러나는가?
- 보안·규제·비가역 데이터 변경은 조건 하나만으로도 ADR 후보로 다뤘는가?
- 미확정 사실을 확정 사실처럼 쓰지 않았는가?

## 수명주기

| 현재 상태 | 허용 전이 | 필요한 근거 |
|---|---|---|
| Proposed | Accepted | 사람의 명시 승인과 프로젝트 승인 절차 |
| Proposed | Deprecated 또는 철회 상태 | 채택하지 않은 이유와 프로젝트 규약 |
| Accepted | Superseded | 대체하는 새 ADR과 양방향 링크 |
| Accepted | Deprecated | 더 이상 적용되지 않는 범위·시점·마이그레이션 설명 |

상태 이름은 프로젝트 규약을 우선한다. `Accepted`의 실질 결정을 바꾸는 편집은 허용 전이가 아니며 새 ADR이 필요하다.

## 구조 검토

- Context가 해결책을 미리 결론내리지 않는가?
- Decision이 무엇을 선택했는지 구체적인가?
- Consequences가 장점과 비용을 모두 담는가?
- Alternatives가 실제 검토한 선택지만 담는가?
- 기각 이유가 선호가 아니라 결정 동인에 연결되는가?
- 관련 ADR, 충돌 ADR, 대체 관계가 링크되는가?
- frontmatter 상태와 본문 상태가 일치하는가?

## 증거·안전 검토

- 저장소 사실과 외부 자료가 구분되는가?
- 외부 자료는 직접 링크와 확인일이 있는가?
- 라이선스가 불명확한 문구나 코드를 그대로 복사하지 않았는가?
- 토큰·시크릿·개인 인증 코드가 포함되지 않았는가?
- ADR 승인, 구현 승인, 머지 승인을 하나의 승인으로 합치지 않았는가?

## goal-cycle 악수 검토

- ADR 경로와 `Accepted` 상태가 확인되는가?
- 결정 한 줄과 구현 제약이 같은 의미인가?
- 후속 작업이 승인된 결정의 범위를 넘지 않는가?
- 미해결 위험과 별도 사람 게이트가 전달되는가?
- Plan·전역 쓰기·배포·머지 등 남은 사람 게이트가 이름까지 보존되는가?
