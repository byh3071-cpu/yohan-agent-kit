# Visual comparison

사용자가 무엇을 고를 수 있어야 하는지 먼저 파악한다. 관련 앱·웹의 공통 기준은 yohan-core `references/design-workflow.md`에 있으며, 해당 작업에서 필요한 경우만 참고한다.

## 비교 방식

| 결정 | 우선 사용할 결과 |
|---|---|
| 어떤 레퍼런스 특징을 가져올지 | 기존 스크린샷·원본 링크와 특징을 짚는 짧은 설명 |
| 시각적 분위기·정보 배치 | 같은 콘텐츠·화면 크기의 대표 화면 이미지 또는 기존 캔버스 |
| 메뉴·입력·전환의 사용감 | 기존 앱의 같은 화면에서 동작만 바꾼 작은 구현 |
| 독립 시연·반복적인 전환 비교 | 공통 구성과 데이터 하나에 변형만 바꾸는 작은 HTML/기존 프리뷰 |
| 변경 내용·검사 결과 전달 | 채팅의 짧은 문장·표·관련 캡처. HTML 보고서는 명시 요청이나 실제 상호작용 필요 시만 |

- 방향이 이미 명확하면 한 안을 구현한다. 모호한 선택은 우선 차이가 분명한 두 안으로 좁힌다. 사용자가 수를 지정하면 따른다. 5~6개를 기본 생성하지 않는다.
- 정보 구조·주요 행동·밀도·시각적 성격 중 비교할 차이를 설명한다. 색상만 바꾼 전체 페이지를 여러 안으로 내지 않는다.
- 같은 실제 콘텐츠, 대표 데이터, 화면 크기, UI 상태로 비교한다. 두 안 모두 읽을 수 있는 문구·계층·정렬·사용 가능한 주요 행동을 갖춘다.
- 참고 자료는 현재 결정에 필요한 만큼만 찾는다. frontend-design은 큰 시각 변경에서 선택하고, 특정 검색 MCP나 여러 생성 서비스를 필수 호출하지 않는다.
- 서비스가 이미지/캔버스를 제공하면 그대로 비교한다. 채택한 안의 코드만 가져와 기존 앱에 연결한다. 이미지·DOM·HTML 전체를 반복 출력하지 않는다.
- HTML이 필요하면 공통 컴포넌트·데이터·스타일을 재사용하고 다른 부분만 전환한다. 기존 프리뷰나 Storybook이 있으면 활용하며 비교를 위해 새 프레임워크를 설치하지 않는다.
- 사용자 선택·구체적 피드백이 오면 해당 부분만 수정한다. 수정 이유 없이 후보 전체를 재생성하거나 스스로 점수를 매기며 반복하지 않는다.
- 제품의 기존 브랜드·아이콘 규칙을 따른다. Studio 전용 자산을 무관한 제품·보고서에 자동 삽입하지 않는다.

## 전달

실제로 볼 수 있는 이미지·원본 캔버스·기존 프리뷰 링크와 각 안의 차이, 추천 이유를 짧게 전달한다. HTML·QA 파일·평가 모델·commit을 기본 산출물로 요구하지 않는다. 채택 코드·자산은 소유 프로젝트가 갖고, 코드에 드러나지 않는 선택·제외 이유만 필요한 기존 기록에 남긴다.
