# 앱·웹 디자인 작업의 공통 기준

정본: Agent Kit `plugins/yohan-core/references/design-workflow.md`. Codex와 Claude Code 어느 쪽에서 시작해도 소유 프로젝트의 코드·자산·합의한 제외 기준을 사용한다. 새 디자인·큰 리디자인에서 필요한 부분만 참고한다.

- 대화·기존 화면에서 사용자, 핵심 행동, 실제 콘텐츠와 범위를 파악한다. 디자인 용어로 다시 설명하라고 요구하지 않는다. 참고 자료는 불명확한 시각 표현·정보 구조·조작 방식을 해결하는 만큼만 찾고 가져올 특징을 정한다.
- 기능·문구·장식은 사용자의 행동이나 결정에 도움이 될 때 넣는다. 제품의 콘텐츠와 맥락으로 개성을 만들고, 완성품처럼 보이게 하려고 무관한 기능·설명·카드를 추가하지 않는다.
- 사용감이 불명확하면 핵심 행동 하나를 끝까지 조작할 수 있는 작은 구현을 먼저 만든다. 방향이 맞으면 확장한다. 해석이 크게 갈릴 때만 작은 비교안을 제시한다. 모든 작업에 인터뷰·다중 시안·별도 승인 단계를 붙이지 않는다.
- “답답함”, “뭘 눌러야 할지 모르겠음”, “글이 불필요함”을 밀도·주요 행동·문구 역할·조작 단계의 구체적인 변경으로 풀어낸다. 취향 피드백·관찰된 사용성 문제·기능 오류가 수정 범위의 근거다.
- 사용자가 제외한 요소는 실제 컴포넌트·문구·템플릿에서 제거한다. 코드로 보이지 않는 제외 이유만 기존 디자인 기록이나 필요한 Dev Log 한 곳에 남긴다. 다음 리디자인에서 기본 템플릿을 이유로 되살리지 않는다.

## 작업에 맞는 도구만 선택

| 작업 | 필요한 조합 |
|---|---|
| 작은 화면·문구 수정 | 기존 코드와 해당 동작 확인 |
| 새로운 시각 방향·큰 리디자인 | `frontend-design` 지침과 필요한 경우 생성 도구 하나 |
| Figma 시안 구현·편집 | 해당 Figma 도구의 구현/편집 스킬과 MCP |
| 전환·터치·키보드·모션 사용감 개선 | 필요한 `emil-design-eng` 지침과 실행 앱 |

Stitch는 공식 MCP가 실제 연결·인증된 경우에, Claude Design은 해당 클라이언트와 계정이 제공하는 경우에 사용한다. Figma는 현재 좌석·파일 권한 안에서 사용한다. 도구가 노출된 것과 인증·쓰기 성공을 구분한다. 두 환경에서 지원이 다르면 지원되는 내보내기 파일·코드·자산으로 이어가며, 미지원 호출을 흉내 내지 않는다.

요청 → 필요한 도구 → 소유 프로젝트 코드 반영 → 실제 핵심 동작 확인으로 진행한다. Stitch·Figma·Claude Design을 매번 모두 거치지 않는다. 생성 HTML·이미지를 기존 앱의 컴포넌트·데이터·스타일 체계에 통합한다. 디자인 도구는 참조·편집 표면이며 코드 정본을 자동으로 양방향 덮어쓰지 않는다.

변경한 화면과 관련된 모바일·빈 상태·오류 상태·접근성을 필요한 만큼 직접 확인한다. 관련 검사 결과를 재사용하고, 임의 품질 점수·평가 에이전트·무한 수정·자동 기록을 추가하지 않는다. 예약 작업·상시 watch·매 편집 훅은 기본값이 아니다. 새 연결·키 발급·약관 수락·결제·비공개 자료의 새로운 외부 전송은 해당 승인 경계를 따른다.

## 비교 비용과 품질을 함께 다루기

- 먼저 이번에 결정할 것을 좁힌다: 레퍼런스 특징, 화면의 계층·배치, 시각적 성격, 실제 조작 중 무엇이 불명확한지 파악한다. 사용자에게 긴 디자인 용어 인터뷰를 요구하지 않는다.
- 레퍼런스는 기존 이미지와 링크에 필요한 특징을 짚어 비교한다. 비교 보드 전체를 HTML로 다시 구현하지 않는다.
- 분위기·배치만 고를 때는 같은 실제 콘텐츠·화면 크기의 대표 화면을 이미지나 기존 캔버스에서 본다. 방향이 명확하면 한 안, 갈리면 우선 차이가 분명한 두 안으로 시작한다. 사용자가 요청한 수가 있으면 따른다.
- 사용감은 정지 이미지로 판단하지 않는다. 기존 앱의 핵심 행동 하나를 실제로 조작하게 만들고, 공통 코드와 데이터에 필요한 변형만 둔다. 단일 HTML은 독립 시연이 필요하거나 기존 앱이 없을 때 선택한다.
- 모든 후보를 전체 앱으로 만들지 않는다. 선택한 안의 코드·자산만 기존 프로젝트로 가져오고 변경한 부분을 수정한다. 이미 받은 화면·도구 결과를 다시 조회하거나 원본 HTML·DOM 전체를 반복 출력하지 않는다.
- 후보는 같은 콘텐츠·상태·화면 크기에서 비교하고 읽기·계층·정렬·주요 행동이 충분히 드러나게 만든다. 원시 와이어프레임과 완성 시안을 비교하거나 색만 바꾼 후보를 창의적 대안으로 세지 않는다. 필요한 시각·상호작용 품질은 유지하고 구현 범위를 줄인다.
- 디자인 MCP와 생성 서비스는 탐색이 필요할 때 하나를 선택한다. 이미지/캔버스 결과로 먼저 선택하고 코드 회수는 채택한 안에 한정한다. API 호출 수와 실제 생성 비용을 확인하지 않고 절감 비율이나 무료 사용을 단정하지 않는다.
- 작은 수정은 추가 스킬 없이 진행한다. 큰 시각 변경은 frontend-design, 상호작용은 필요한 emil-design-eng, 지정 Figma 작업은 해당 Figma 스킬을 선택한다. visualize는 비교가 필요한 경우, design-to-html은 선택한 시안의 구현이 필요한 경우만 쓴다. 디자인 팀·평가·다중 모델·보고 스킬을 자동 연쇄하지 않는다.
- 자동화는 사용자의 작업 요청에서 시작해 관련 맥락 읽기 → 필요한 최소 비교 → 선택한 부분 구현 → 직접 조작 확인으로 이어진다. 새 피드백이나 오류가 없는 추가 생성·평가·상시 watch는 시작하지 않는다.
- 코드에서 제거한 요소는 실제 컴포넌트·템플릿에서 제거하고, 코드에 보이지 않는 제외 이유만 기존 한 곳에 남긴다. 매 작업의 새 취향 문서·QA 보고서·디자인 시스템을 만들지 않는다.
