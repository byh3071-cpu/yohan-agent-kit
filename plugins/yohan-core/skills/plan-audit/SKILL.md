# plan-audit — 역추출 대조 감사

계획을 승인하기 전에 건다. **기존 `cross-check`와 시점이 다르다** — cross-check는 산출물의 내적 건전성, 이 스킬은 *요청 원문 ↔ 계획*의 정합.

## 왜 블라인드인가

잡으려는 결함은 계획의 버그가 아니라 **요청→계획 번역에서 떨어진 정보**다.
감사자가 계획을 먼저 읽으면 앵커링돼서 "빠진 것"은 구조적으로 못 본다.
그래서 **어느 서브에이전트에게도 계획을 주지 않는다.**

- `critic` → 사용자 발화만 받는다
- `explorer` → "이 파일 N행에 뭐가 있나" 같은 **사실 질의만** 받는다. 계획이 뭐라고 주장하는지는 모른다
- 대조는 지휘자(메인)가 한다

앵커링 차단은 인용 검증에도 그대로 적용된다. 지휘자가 직접 `sed -n '22p'`로 읽고 판정하면 계획을 이미 아는 상태라 "맞겠지" 하고 넘어간다. explorer는 계획을 모르니 사실만 돌려주고, 대조는 그 다음이다.

계획 사본 파일을 만들지 않는 게 핵심이다. 파일이 없으면 우연히 읽을 경로도 없다.

**다만 블라인드는 절대적이지 않다.** 사용자가 발화에서 계획을 인용하거나 통째로 붙여넣으면(반려 지시가 특히 그렇다) 그건 원문의 일부라 critic에게 그대로 간다. 이건 막을 수 없다 — 사용자 발화를 검열하면 기준선이 오염되고, 그게 더 큰 손해다.

막는 건 **경로를 통한 누수**뿐이다: 계획 파일·`decisions` 파일·산출 디렉터리 탐색. 발화 경유 누수가 의심되면 판정에 `[누수 있음]`을 표기하고, 그 항목의 "누락 아님" 판정을 약한 근거로 취급해라.

## 절차

### 0. 대상 확인
감사할 계획이 지휘자 컨텍스트에 있어야 한다. 없으면 **즉시 중단**하고 무엇을 감사할지 물어라.

**⚠ `~/.claude/plans/` · `.cursor/plans/` 에 파일이 있다 ≠ 감사 대상이 있다.**

플랜 모드에 다시 들어가면 하네스가 **이전 계획 파일을 그대로 재사용**한다. 그 안의 계획은 이미 승인·실행·머지까지 끝났을 수 있다.

> 실측: 이 스킬 세션에서 **머지 완료된 계획서**를 감사 대상으로 잡고 진입했다. description만 보는 블라인드 판정자는 같은 상황을 "미발동"으로 정확히 갈랐다 — 문서가 아니라 실행이 틀렸다.

파일을 대상으로 삼기 전에 셋 다 확인해라.

1. 이 계획을 **이번 대화에서** 세웠나?
2. 계획이 말하는 변경이 **이미 적용돼 있지 않나?** (`git log`·파일 상태로 대조)
3. 계획서에 완료 표시(체크·"머지 완료"·버전 bump 흔적)가 있지 않나?

**하나라도 걸리면 감사 대상이 아니다.** 발동 조건 (2)는 `아직 승인이 안 났고`이고, 승인도 실행도 끝난 계획은 이 스킬의 범위 밖이다 — `cross-check` 로 보내라.

이건 발동 *후*의 방어선이다. description 단계에서 이미 걸러졌어야 하지만, stale 파일은 하네스 거동이라 스킬이 막을 수 없다. 여기서라도 빠져나와라.

### 1. 원문 추출
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "<스크립트경로>" -Engine auto
```
스크립트 경로는 `$env:CLAUDE_PLUGIN_ROOT\skills\plan-audit\scripts\Export-UserTurns.ps1`.
**`${CLAUDE_PLUGIN_ROOT}` 리터럴을 그대로 넘기지 마라** — 확장되지 않아 죽는다.
변수가 비어 있으면 Glob으로 `**/skills/plan-audit/scripts/Export-UserTurns.ps1` 절대경로를 해석해 넘겨라.

#### Engine
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "<스크립트경로>" -Engine auto   # 기본
powershell -NoProfile -ExecutionPolicy Bypass -File "<스크립트경로>" -Engine claude
powershell -NoProfile -ExecutionPolicy Bypass -File "<스크립트경로>" -Engine cursor -TranscriptPath "<cursor-jsonl>"
```
- `auto` — `CLAUDE_CODE_SESSION_ID` 있으면 claude; 아니면 Cursor `agent-transcripts` 유무·경로로 cursor/claude 선택
- **Cursor 채팅/에이전트 세션에서는 `-Engine cursor`를 명시하라.** `auto`는 같은 셸에 `CLAUDE_CODE_SESSION_ID`가 남아 있으면 claude로 잘못 분기할 수 있다.
- `claude` — `~/.claude/projects` jsonl · `promptSource=typed` 경로
- `cursor` — `~/.cursor/projects/*/agent-transcripts/*/*.jsonl` · `<user_query>` 추출 (`promptSource` 불필요)

**스크립트 exit ≠ 0 이면 HARD STOP.** summary critic 돌리지 마라. 감사 = **FAIL**. 폴백 발화 요약·재구성 금지.

스크립트는 **파일 두 개**를 낸다. 섞으면 안 된다.

| 종류 | 산출 파일 | critic 에 주나 |
|---|---|---|
| **직접 입력** (`promptSource=typed` / Cursor `<user_query>`) | `requests-<sid>.txt` | ✅ |
| **반려 지시** — 도구·계획을 반려하며 남긴 말. `tool_result`에 묻혀 있어 놓치기 쉽지만 **이 스킬의 핵심 입력**이다 (claude) | `requests-<sid>.txt` | ✅ |
| **선택지 응답** — `AskUserQuestion` 으로 사용자가 고른 답 (claude; cursor 는 best-effort/absent) | `decisions-<sid>.txt` | ❌ **절대 금지** |

`requests-<sid>.txt` 를 Read 한다. **`decisions-<sid>.txt` 는 지휘자만 읽고, 절차 3(대조)에서 쓴다.**

선택 라벨에는 **어시스턴트 제안의 요지**가 들어 있다. critic 프롬프트에 섞으면 앵커링돼서 이 스킬의 존재 이유가 사라진다 — 그래서 스크립트가 파일을 갈라 놓는다.

실행 중 `AskUserQuestion 레코드는 감지됐는데 수집이 0건이다` 경고가 뜨면 **하네스 마커가 바뀐 것**이다. 그 상태로 "근거 없음" 판정을 내리지 마라.

#### Role contracts
- **blind-extractor** ≈ `critic` — 발화만 보고 요구사항 목록. 계획 금지
- **fact-oracle** ≈ `explorer` — 경로·행·심볼 사실 질의만. 계획 주장 모름
- 호스트에 `Task`/서브에이전트 이름이 다르면 **역할에 맞는 것**으로 매핑해라 (이름 고착 금지)

### 1b. 계획에서 검사 대상 뽑기
**세 종류**로 나눠 목록화한다. 성격이 달라 처리 방법이 다르다.

| 종류 | 예 | 처리 |
|---|---|---|
| **기존 경로·심볼** (지금 있나?) | `docs/patterns/PAT-001.md`, `Export-UserTurns.ps1` | 2-A. Bash |
| **신규 생성 예정** (아직 없는 게 정상) | "`decisions-<sid>.txt` 를 새로 만든다", "`Get-ShortTs` 함수 추가" | **존재 확인 대상 아님** |
| **인용** (그 내용이 맞나?) | `critic-gate.ps1:22`, "PAT-001이 X를 처방한다" | 2-B. explorer |

**⚠ 이 분류를 먼저 해라. 안 하면 거짓 고발이 난다.**

계획이 *만들겠다*고 한 것을 존재 확인에 넣으면 부재가 나오고, 판정 5(근거 실존)는 치명이라 **규칙을 정확히 따랐는데 불통과**가 된다. 계획서에 "생성한다 / 추가한다 / 신설한다"로 적힌 대상은 2-A에서 빼라.

거꾸로, 신규 생성 예정인데 **이미 존재하면** 표기한다 — FAIL은 아니지만 계획이 덮어쓰기를 인지 못 했다는 신호다.

인용이 하나도 없으면 2-B를 스킵한다.

### 2-A. 존재 확인 — Bash 직접

**대상은 1b에서 "기존"으로 분류한 것뿐이다.** 계획이 새로 만들겠다는 것은 넣지 마라 — 부재가 나오고 판정 5(치명)에 걸린다.

LLM이 필요 없다. 판단이 안 들어가므로 서브에이전트로 돌리면 느리고 비싸기만 하다.
```bash
for p in <경로들>; do if [ -e "$p" ]; then echo "OK   $p"; else echo "MISS $p"; fi; done
```
심볼은 `Grep`으로 확인하되 **정의를 찾아라. 이름이 나오는 것만으로 통과시키지 마라.**

문서·주석·호출부·문자열 안에 이름만 있어도 검색은 걸린다. 계획이 "`Get-ShortTs` 를 쓴다"고 했는데 실제로는 주석에만 있는 경우, 이름 검색은 통과하고 계획은 깨진다.

| 대상 | 정의 패턴 |
|---|---|
| PowerShell 함수 | `^function\s+Name` · `^\s*\$Name\s*=` |
| JS/TS | `(function\|const\|let\|class)\s+Name` · `export .*Name` |
| 스킬·문서 앵커 | `^#+ .*Name` · frontmatter `name:` |

대소문자도 그대로 맞춰라 — `-i` 를 붙여 찾은 건 "있다"의 근거가 아니다.

### 2-B. 인용 검증 — explorer(haiku) 위임

**계획이 뭐라고 주장하는지 알려주지 마라.** 사실 질의만 던진다.
- ✅ "`plugins/yohan-core/hooks/critic-gate.ps1` 22행이 무슨 내용인지 그대로 인용해라"
- ✅ "`docs/patterns/PAT-001-*.md`의 '해결' 항목이 처방하는 게 뭔지 요약해라"
- ❌ "계획이 22행을 `permissionDecision='ask'`라고 인용했는데 맞나?" ← 답을 알려주면 앵커링

받은 사실을 지휘자가 계획의 주장과 대조한다.

### 2-C. 블라인드 요구사항 추출 — critic(opus) 위임

2-A·2-B와 **한 메시지에서 병렬**로 던진다. 서로 독립이다.

사용자 발화 전문을 프롬프트에 **verbatim 임베드**해서 넘긴다.
- 금지 지시를 반드시 포함:
  - `~/.claude/plans/` · `.cursor/plans/` 읽지 마라 · "계획/플랜" 파일 탐색하지 마라
  - **`decisions-*.txt` 를 읽지 마라** — 선택 라벨에 어시스턴트 제안의 요지가 들어 있다
  - **산출 디렉터리를 목록으로 훑지 마라.** 넘겨받은 `requests` 파일 하나만 읽어라
  - 무엇이 이미 설계됐는지 몰라야 한다
- 산출 요구: **요구사항 / 제약 / 성공조건 / 명시적 금지·비범위 / 모호한 지점** 5개 목록, 번호 부여
- 각 항목에 **원문 인용** 필수 — 근거 없는 항목을 원천 차단
- "발화에 근거 없으면 '발화에 없음'이라고 써라. 추측으로 채우지 마라"

원문이 50KB를 넘으면 임베드 대신 파일 경로를 넘긴다. **`requests-<sid>.txt` 절대경로 하나만** 준다 — `decisions-<sid>.txt` 가 같은 폴더에 있으므로, 디렉터리를 알려주거나 `plan-audit` 산출 위치를 언급하면 한 번의 `Glob`으로 뚫린다.

모델 티어는 **opus 유지**. 감사가 헐거우면 존재 이유가 없다. 요구사항 추출은 기계적으로 보이지만, 실측상 모호지점 11개를 잡아낸 건 opus급 판단이었다.

### 3. 대조
critic 목록 ↔ 계획을 매핑한다.

**⚠ 먼저 발화 경계를 그어라. 세션 ≠ 작업.**

추출기는 트랜스크립트 **전체**를 뽑는다. 한 세션에서 작업을 두세 개 했으면 이전 작업·철회된 요구·감사 요청 자체까지 전부 들어 있다. 그걸 그대로 대조하면 **이전 작업의 요구사항이 현재 계획의 "누락"(치명 1)으로 잡혀 자동 불통과**한다.

각 `TURN`·`DECISION` 에 **UTC 시각**이 붙어 있다. 대조 전에:

1. 감사 대상 계획이 **제시된 시각**을 정한다
2. 그 이전 발화는 `[이전 작업]` 으로 표기하고 **누락 판정에서 제외**한다
3. 경계가 애매하면 사용자에게 한 줄로 물어라 — 조용히 넓게 잡지 마라

경계 밖 발화도 버리지는 마라. **제약·금지는 세션 전체에 걸쳐 유효할 수 있다**(예: "커밋은 건들지마"). 누락 판정에서만 빼고, 제약으로는 계속 본다.

- 계획에 매핑 안 되는 요구사항 → **누락**
- 계획에 있는데 원문 근거 없음 → **스코프 크립** (단, 레포 관례·글로벌 규칙 유래면 그렇게 표기하고 통과)
- 요구사항이 다른 뜻으로 기술됨 → **왜곡**

> critic이 뽑은 항목만 *사용자 합의 사항*이다. 어시스턴트가 제안하고 사용자가 고른 것은 요구사항이 아니라 **채택된 제안**이다. 이 구분을 대조표에 남겨라.

**⚠ "발화에 없음" ≠ "근거 없음".**

원문에 `ㅇㅇ`·`ㅇㅋ`·`A`·`머지해` 같은 **내용 없는 수락 신호**가 있으면, 그 턴의 결정 내용은 원문 밖에 있다. 원문에는 승낙만 남는다.

→ 스코프 크립으로 판정하기 전에 **`decisions-<sid>.txt` 를 먼저 대조해라.** 거기서도 못 찾을 때만 근거 없음이다.

`decisions` 는 **두 채널**을 담는다. 종류가 각 항목에 표기된다.

| 종류 | 출처 | 복원되는 것 |
|---|---|---|
| `(선택지)` | `AskUserQuestion` 응답 | 질문 + 사용자가 고른 라벨 |
| `(평문 수락)` | 짧은 발화 + **직전 어시스턴트 발화** | 무엇을 승낙했는지 |

`0.3.15`는 선택지 채널만 메우고 "결정 내용은 선택지 UI에 있다"고 단정했다 — **틀렸다.** 평문 제안에 `ㅇㅇ`로 답한 경우가 실측상 더 많았고(이 스킬 세션: 선택지 5 · 평문 16), 그쪽은 `decisions`에도 없어서 같은 오판이 재발할 수 있었다.

`수락 신호 N건에 직전 어시스턴트 발화가 없다` 경고가 뜨면 그 건은 **어느 파일로도 복원 안 된다.** 트랜스크립트를 직접 봐라.

**경고를 무시하지 마라 — 각각 판정을 뒤집는다.**

| 경고 | 뜻 | 하지 말아야 할 것 |
|---|---|---|
| `마커를 한 건도 못 찾았다` | 채널이 통째로 안 보임 | "근거 없음" 판정 |
| `N건이 수집도 배제도 안 된 채 사라졌다` | 파서가 새는 중 | `decisions` 기준 "결정 없음" 단정 |
| `응답 형식이 아니라 배제했다` | 로그·문서에 인용된 마커를 걸러냄 (**정상**) | — |
| `후행 래퍼를 못 찾아 끝까지 캡처했다` | 하네스 문구가 발화에 섞였을 수 있음 | 해당 TURN 꼬리를 안 보고 넘어가기 |

이 조건을 넓히지 마라. *수락 신호가 원문에 있을 때*로 한정한다 — 모든 "발화에 없음"을 의심하기 시작하면 스코프 크립 탐지가 통째로 무력해진다.

> 실측(`0.3.14`): 이 규율이 없어서 "커밋 금지 해제에 사용자 근거가 없다"고 **거짓 고발**했다. 실제로는 `AskUserQuestion` 에 명시 승인이 있었고 추출기가 못 봤을 뿐이다. 감사 도구의 사각은 거짓 통과가 아니라 **거짓 고발**로 나타난다.

### 4. 입도 검사
계획의 각 단계를 3기준으로 본다: **1커밋 · 독립 검증가능 · 롤백가능**.

### 5. 판정 출력

| # | 항목 | FAIL 조건 |
|---|---|---|
| 1 | 의도 정합 | 추출 요구사항 중 계획에 매핑 안 되는 항목 존재 |
| 2 | 스코프 크립 | 계획에 있는데 원문 근거도 출처 표기도 없는 항목 존재 |
| 3 | 왜곡 | 요구사항이 다른 뜻으로 구현되게 기술됨 |
| 4 | 분해 입도 | 1커밋·독립검증·롤백 중 하나라도 못 맞추는 단계 존재 |
| 5 | 근거 실존 | **기존** 경로·심볼로 분류된 것이 부재(2-A), 또는 인용 내용이 실제와 다름(2-B) — **신규 생성 예정분의 부재는 FAIL 아님**(1b) |
| 6 | 미확인 가정 | 계획이 전제하는데 검증 안 된 사실이 명시 안 됨 |
| 7 | 검증 계획 | 통과 판정 기준 없는 단계 존재 |

**치명(1·3·5) 하나라도 걸리면 불통과.** `critic` 판정 규율과 같다.

모호한 지점이 남아 있으면 PASS라도 함께 표시한다 — 발화가 짧으면 기준선이 빈약해 거짓 PASS가 난다.

### 6. 2회차 재진입 — 여기서 멈추지 마라

5의 지적표를 근거로 **수정안을 작성한다. 계획에 적용하지는 않는다.**
그리고 **그 수정안을 대상으로 2~5를 한 번 더 돈다.** 사용자에게 물어보지 말고 바로 이어서 한다.

- 2회차 대상 = **1회차가 새로 쓴 문장뿐**. 손대지 않은 부분은 다시 안 판다
- 2회차에서도 결함이 나오면 수정안을 고치고, 그건 3회차 후보로 표시만 한다(자동 진행 금지)
- 2회차까지 끝나면 **두 회차 결함을 합쳐 한 번에** 사용자에게 낸다

**왜 적용하지 않고 제안에 머무는가:** 계획 수정은 사용자 승인 사항이다. 감사자가 계획을 고쳐 적용하면 승인 게이트를 우회하게 되고, 그건 이 스킬이 잡으려는 결함(스코프 크립)을 스스로 저지르는 꼴이다. 수정안 상태로 두면 2회차를 도는 데 아무 지장이 없다 — 실측상 2회차 결함은 전부 "1회차에서 새로 쓴 문장"에서 나왔고, 그 문장은 적용 여부와 무관하게 존재한다.

## 출력

한국어 반말·두괄식(`yohan-writing`). **지적표 → 수정안**까지. 계획 재작성·적용은 사용자 승인 후 지휘자가 한다 — 감사자가 저자가 되면 독립성이 무너진다.

1·2회차 결함을 회차별로 구분해 한 표에 낸다. 끝에 **남은 각도**(3회차 후보)를 제시하고 더 팔지는 사용자에게 넘긴다.

## 회차 운영 — 1·2회차는 호출 1번에 자동으로 돈다

한 번으로 안 끝난다. 실측상 회차마다 새 결함이 **직전 회차의 수정문**에서 나온다.
멈추는 기준은 "결함 0"이 아니라 **"새로 추가한 문장이 더 이상 새 결함을 안 낳을 때"**.

| 회차 | 대상 | 각도 | 자동/수동 |
|---|---|---|---|
| 1 | 원 계획 | 환각 스캔 + 블라인드 요구사항 대조 | **자동** — 호출 즉시 |
| 2 | **1회차 수정안**(적용 전) | 수정안이 새로 들인 인용·전제·근거 | **자동** — 절차 6으로 이어서 |
| 3+ | 누적 수정안 | 자기 루브릭 적용 · 실행 가능성 · 벤더 교차(Codex) | **수동** — 사용자가 결정 |

1·2회차는 각도가 고정이라 매번 똑같이 돌면 되므로 자동화한다. 사용자가 매번 "검증 및 리뷰"를 다시 치게 만들지 마라 — 실측상 그 반복이 이 스킬을 만든 이유다.

**1회차와 2회차는 대상이 다르다.** 1회차 2-B가 검사하는 건 *원 계획의* 인용이고, 2회차가 검사하는 건 *수정안이 새로 들인* 인용이다. "이미 인용 검증했다"고 2회차를 건너뛰지 마라 — 새 문장은 아직 아무도 안 봤다.

3회차부터는 각도 선택에 판단이 들어가므로 자동화하지 않는다.

### 오발동 차단 — use / mention 구분

같은 문구가 **요청**일 수도 있고 **문구를 가리키는 것**일 수도 있다. 실제로 한 대화에서 둘 다 나왔다.

| 발화 형태 | 감사할 계획 | 판정 |
|---|---|---|
| 단독 발화 (동사·어미 있음) — `검증 및 리뷰.` | 있음 · 미승인 | **발동** |
| 따옴표·중간점 나열 — `"검증 및 리뷰" · "빠진 거 없어"` | 있음 · 미승인 | **한 줄 되묻기** |
| 무엇이든 | 없음 | **발동 안 함** → `cross-check` |

**나열을 인용으로 단정하지 마라.** 실측에서 사용자가 `그럼 실제로 지금 해볼게.` 직후에 문구를 나열했고, 본인도 나중에 "그때 나도 헷갈렸다"고 답했다. 나열은 트리거 시도일 수도, 문구를 논의하는 자리일 수도 있다 — 한쪽으로 단정하면 어느 쪽이든 절반은 틀린다.

되묻기는 **평문 한 줄**이다. **이 되묻기에는** 설문 UI(`AskUserQuestion`)를 쓰지 마라 — 되묻는 비용이 감사보다 커진다.

전면 금지가 아니다. 감사 끝에 **설계 분기를 사용자에게 넘길 때**는 설문 UI가 맞다(그 응답은 `decisions-<sid>.txt` 로 남아 다음 회차 감사의 근거가 된다). 금지되는 건 *발동할지 말지* 묻는 자리뿐이다.

```
이 문구들로 지금 계획 감사 돌릴까? (ㅇ/ㄴ)
```

`ㅇ`·`ㅇㅇ`·`ㄱㄱ` 계열이면 절차 1부터 정상 진행. `ㄴ`이거나, 답 없이 다른 주제로 넘어가면 발동하지 않는다. **애매하면 발동하지 않는 쪽으로 넘어가라** — 원치 않는 감사는 마찰이지만, 안 돈 감사는 사용자가 한 번 더 치면 된다.
